1. ¿Qué es Django y por qué lo usaríamos?
Django es un framework web de alto nivel escrito en Python que fue desarrollado en un entorno periodístico de ritmo acelerado, y por eso está diseñado para que las tareas comunes del desarrollo web sean rápidas y sencillas.⁠
⁠ Lo usaríamos porque trae resuelto "de fábrica" casi todo lo que una aplicación web con base de datos necesita: un ORM para describir el esquema de la base en código Python, un sistema de URLs limpias, un motor de templates con herencia, un panel de administración generado automáticamente a partir de los modelos, autenticación, formularios, migraciones, caché y feeds RSS/Atom. Sigue la filosofía batteries included y DRY (no repetirse), lo que permite construir aplicaciones seguras y escalables sin reinventar cada componente.
2. ¿Qué es el patrón MTV y cómo se compara con MVC?
MTV (Model-Template-View) es la interpretación que hace Django del clásico MVC: el Model define los datos y su lógica de persistencia, el Template define la presentación (el HTML con variables y tags), y la View contiene la lógica que decide qué datos traer y qué template renderizar. La comparación es casi una cuestión de nombres: el Model de MTV equivale al Model de MVC, el Template de Django cumple el rol de la View de MVC (la capa visual), y la View de Django ocupa el lugar del Controller de MVC. La diferencia conceptual clave es que en MTV no escribís el controlador: el propio framework hace de controlador, ya que es Django quien recibe la petición, la resuelve contra el URLconf y llama a la vista correspondiente. Por eso se dice que MTV es un MVC "simplificado", donde además cada pieza (modelos, vistas, templates) está desacoplada de la siguiente y podés reemplazarla por otra si querés.⁠

3. ¿Qué entendemos por app en Django?
Una app en Django es un módulo o paquete de Python autocontenido que implementa una funcionalidad específica del sitio —por ejemplo news, usuarios, blog o carrito— y que típicamente agrupa sus propios models.py, views.py, urls.py, admin.py, templates/ y migraciones. La distinción importante es entre proyecto y app: el proyecto es la configuración global del sitio (settings.py, urls.py raíz, wsgi.py/asgi.py) y puede contener muchas apps, mientras que una app está pensada para ser reutilizable e incluso instalable en otros proyectos (Django mismo trae apps como django.contrib.admin o django.contrib.auth). Se crean con python manage.py startapp nombre y se activan agregándolas a la lista INSTALLED_APPS.
4. ¿Qué es el flujo request-response en Django?
Es el ciclo por el cual una petición HTTP entra al framework y sale convertida en una respuesta: el servidor WSGI/ASGI recibe la petición y Django la envuelve en un objeto HttpRequest, que pasa primero por la cadena de middleware (sesiones, autenticación, CSRF); luego el URLconf recorre cada path en orden y se detiene en el primero que coincide con la URL pedida, pasándole a la vista el objeto request más los valores capturados en el patrón —y si ninguno coincide, Django invoca una vista especial de 404.⁠
⁠ La vista tiene una única responsabilidad: devolver un HttpResponse con el contenido de la página o lanzar una excepción como Http404; generalmente consulta los modelos con el ORM, carga un template y lo renderiza con los datos obtenidos.⁠
⁠ Esa respuesta vuelve a recorrer los middleware en sentido inverso (agregando cookies, headers, compresión) y finalmente se envía al navegador.
5. ¿Qué es el concepto de ORM?
Un ORM (Object-Relational Mapping) es una capa de abstracción que traduce entre objetos de un lenguaje orientado a objetos y tablas de una base de datos relacional: las clases se corresponden con tablas, los atributos con columnas y las instancias con filas, de modo que podés manipular datos escribiendo Python en lugar de SQL. En Django describís el esquema de la base en código Python mediante modelos, y luego makemigrations genera las migraciones para las tablas que no existen y migrate las ejecuta creando efectivamente las tablas.⁠
⁠ A partir de ahí obtenés gratis una API rica y creada al vuelo, sin generación de código, con la que hacés Reporter.objects.all(), Reporter.objects.get(full_name__startswith="John") o Article.objects.filter(reporter__full_name__startswith="John") —siguiendo relaciones tan lejos como necesites mientras Django ejecuta los JOINs eficientes por detrás— y persistís cambios con save() o los eliminás con delete().⁠
⁠ Las ventajas son menos código repetitivo, portabilidad entre motores de base de datos y protección contra inyección SQL; la contrapartida es cierta pérdida de control fino sobre consultas muy complejas.
6. ¿Qué son los templates en Django?
Los templates son los archivos (habitualmente HTML) que definen la presentación, y el sistema de templates de Django tiene varias características potentes pero busca mantenerse lo bastante simple como para que lo usen no programadores.⁠
⁠ Sus elementos son: variables entre dobles llaves, donde {{ article.headline }} significa "mostrá el valor del atributo headline del artículo" y donde el punto sirve además para búsqueda de claves de diccionario, de índices y para llamar funciones; filtros, aplicados con el carácter pipe como en {{ article.pub_date|date:"F j, Y" }}, que pueden encadenarse y también escribirse a medida; y tags como {% for %} o {% block %}, que también admiten versiones personalizadas que ejecutan código Python por detrás.⁠
⁠ La pieza clave es la herencia de templates: {% extends "base.html" %} carga primero una plantilla base que define una serie de bloques y los rellena con los del hijo, lo que reduce drásticamente la redundancia porque cada template define sólo lo que le es propio y un rediseño del sitio se hace cambiando un único archivo.⁠
⁠ Django los busca recorriendo la lista de directorios configurada en DIRS, pasando al siguiente si no encuentra el archivo en el primero, y nada te obliga a usar este sistema: podés reemplazarlo por otro porque cada pieza está desacoplada.⁠

7. Lectura de Django at a glance.
El documento es un recorrido informal por cómo se escribe una app web con base de datos en Django, y su hilo conductor es el ejemplo Reporter/Article de una app news: primero diseñás el modelo en models.py con clases que heredan de models.Model y campos como CharField, TextField, DateField y ForeignKey; después lo instalás en la base con makemigrations y migrate; enseguida disfrutás de la API gratuita del ORM para crear, consultar, modificar y borrar objetos; luego registrás el modelo en admin.py con admin.site.register(models.Article) y obtenés una interfaz de administración profesional y lista para producción —la filosofía es que no deberías tener que construir backends sólo para gestionar contenido, y un flujo de trabajo típico es levantar modelos y admin cuanto antes para que el equipo empiece a cargar datos mientras vos desarrollás la cara pública—; después diseñás las URLs en un URLconf que mapea patrones a funciones y mantiene las URLs limpias, sin .php ni .asp, compilándolas a expresiones regulares al cargar para que el matcheo sea rapidísimo; escribís las vistas, que recuperan datos según los parámetros y renderizan un template con render(); y finalmente diseñás los templates con variables, filtros, herencia y {% load static %}. Cierra aclarando que esto es apenas la superficie y menciona otras funcionalidades útiles como el framework de caché integrable con memcached, el de sindicación para generar feeds RSS y Atom, y un admin autogenerado más completo de lo que alcanzó a mostrar.⁠

8. ¿Cómo se lo instala?
La guía rápida propone una instalación mínima en cuatro pasos. Primero, instalar Python, ya que Django es un framework web de Python; conviene bajar la última versión desde python.org o usar el gestor de paquetes del sistema operativo, y como Python incluye una base de datos liviana llamada SQLite, todavía no hace falta configurar ninguna base —se verifica escribiendo python en la terminal y viendo el prompt >>>.⁠
⁠ Segundo, configurar una base de datos, paso necesario sólo si querés trabajar con un motor "grande" como PostgreSQL, MariaDB, MySQL u Oracle.⁠
⁠ Tercero, instalar Django, para lo cual hay tres opciones: instalar una release oficial (el mejor camino para la mayoría de los usuarios, típicamente con pip install django dentro de un entorno virtual), instalar la versión que provee la distribución del sistema operativo, o instalar la última versión de desarrollo —opción para entusiastas que quieren lo más nuevo, con el riesgo de encontrar bugs y de que los paquetes de terceros sean menos compatibles—; en todos los casos hay que consultar siempre la documentación correspondiente a la versión que estás usando y prestar atención a las partes marcadas como new in development version.⁠
